# Contributing to open-fp

Thanks for helping. open-fp is a DIY golf force plate: hardware (printed parts, load cells, an ADC board), MCU firmware for the Arduino UNO Q, and a Python processing app with a web UI. Contributions in any of those areas are welcome, and so are build reports from people who have made one.

## Ways to help

- **Build one and report back.** Open a [build report or question](https://github.com/open-flight/open-fp/issues/new/choose): what worked, what didn't fit, and what measured differently. Fit and measurement notes end up in [`docs/VERIFIED.md`](docs/VERIFIED.md).
- **Fix or improve the docs.** If a step in [`docs/harness.md`](docs/harness.md) or [`docs/assembly.md`](docs/assembly.md) confused you, it will confuse the next person too.
- **Code:** the processing pipeline and swing detection (`app/python/open_fp/`), the web UI (`app/assets/`), the simulator (`tools/sim/`), the bench tools (`tools/bench/`), and the MCU firmware (`app/sketch/`, `bench/`).
- **Hardware:** CAD changes (`hardware/cad/`), the ADC board (`hardware/pcb/adc-board/`).

For anything bigger than a small fix, open an issue first so we can agree on the approach before you spend time on it.

## Development setup

You don't need any hardware to work on the Python side. The test suite and the simulator run on synthetic data.

```bash
git lfs install                 # CAD files (STL/STEP) are stored in Git LFS
git clone https://github.com/open-flight/open-fp.git && cd open-fp
python3 -m venv .venv && .venv/bin/pip install -r requirements-dev.txt
.venv/bin/pytest                # the whole suite, no hardware needed
.venv/bin/python tools/sim/sim_server.py   # web UI on synthetic swings: http://localhost:7070
```

On macOS, `tools/dev_setup.sh` does all of this and also installs `arduino-cli` with the UNO Q core. For the board itself, follow [`docs/SETUP.md`](docs/SETUP.md).

Before you push, run the same checks CI runs:

```bash
.venv/bin/ruff check app/python tools tests docs/img
PYTHONPATH=app/python:tools/sim:tools/bench .venv/bin/pylint app/python/open_fp tools/sim tools/bench --fail-under=9
.venv/bin/pytest
```

## Pull requests

- **One change per PR.** If the description needs "and also", split it.
- **Fill in the template.** CI checks that "Why was this required?", "Automated tests" and "Manual (human) testing" have real content. Manual testing means what you ran and saw yourself: the simulator, real plates, a printed part.
- **Tests:** a PR that changes Python under `app/python/open_fp/`, `tools/sim/` or `tools/bench/` must add or update tests under `tests/`. A maintainer can add the `no-tests-needed` label when tests genuinely don't apply.
- **Title:** [Conventional Commits](https://www.conventionalcommits.org/) style, for example `fix(swing): detect finish from CoP settling`. Allowed types: `feat`, `fix`, `docs`, `refactor`, `test`, `chore`, `perf`, `build`, `ci`, `style`, `revert`.
- **Keep it reviewable:** under about 50 files and 2000 changed lines. Open PRs from a branch in your fork, not from `main`.

## Hardware changes

- **Record measurements.** Any dimension, fit check, pin change or bench result goes in [`docs/VERIFIED.md`](docs/VERIFIED.md) with the date and how it was checked. That file is how the project tells measured facts from assumptions.
- **CAD:** the committed STEP/STL files are the source of truth. The CadQuery scripts in `hardware/cad/src/` are an older revision (see `docs/VERIFIED.md`), so recent changes were made by editing the STEP in CadQuery and re-exporting both STEP and STL. Say in the PR which approach you used.
- **ADC board:** everything is generated from `hardware/pcb/adc-board/scripts/design.py`. Run `scripts/build.sh` and `scripts/export.sh` and commit the regenerated KiCad files, Gerbers and assembly files together. CI runs ERC and DRC on every PR that touches the board.
- **Diagrams** in `docs/img/` are generated by `docs/img/make_*.py`. Change the script, run it, and commit both. CI fails if they drift.

## Reporting bugs and security issues

Use the [issue templates](https://github.com/open-flight/open-fp/issues/new/choose). For a security problem, don't open a public issue: see [`SECURITY.md`](SECURITY.md).
